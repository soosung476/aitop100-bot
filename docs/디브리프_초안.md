## 1. 나의 AI 에이전트의 강점은 무엇인가요?

제가 만든 에이전트는 답변에서 끝나지 않고 조회와 접수까지 직접 처리합니다. 금액, 날짜, 상태는 액션 API 조회값과 규정 원문만 근거로 안내합니다. 전액환불 금액은 주문 결제액을 기준으로 하고, 이관 회신 기한은 영업일 달력으로 코드가 계산합니다. 접수 API는 정책을 검사하지 않기 때문에 호출 전에 규정과 권한 위임표로 먼저 판단하도록 설계했습니다.

다음 상황을 우선해 설계했습니다. 실수했을 때 고객 피해가 크거나 담당자마다 답이 갈리기 쉬운 상황이라고 판단했기 때문입니다.

- 하자 신고는 안전 확인을 가장 먼저 합니다. 이어서 배송, 로트, 조사 이력을 확인하고 고객의 선택을 받아 접수합니다. 같은 로트에 앞선 신고가 있으면 담당자 이관을 별도로 접수합니다.
- 섭취 후 이상은 인과가 확인되기 전에 배상을 약속하지 않고 정식 배상 절차로 넘깁니다.
- 다른 계정의 주문은 주소를 시·동 단위로도 안내하지 않습니다.
- 규정 개정은 개정마다 적용 기준이 달라 주문 시점과 신고 시점을 구분해 판단합니다.
- 사칭 제보와 위기 신호는 절차서의 순서대로 응대하고, 상품 문제로 축소하지 않습니다.

고객의 사진은 비전 모델로 내용을 글로 옮기고, 음성은 서버의 Whisper로 받아써서 같은 흐름으로 처리합니다. 제주 사투리 음성도 시험했습니다. 답변은 말풍선 하나, 200자 안팎을 기준으로 하고 필요한 정보는 한 번에 묻도록 했습니다.

## 2. 어떤 접근으로 정보를 획득했나요?

관계자 10명을 모두 찾아 인터뷰했습니다. 총 475회 질문했고, 관계자별 발굴률은 56~87%, 단순 평균은 약 72%입니다.

처음에는 넓게 물었더니 답이 얕았습니다. 그래서 받은 문서의 조항, 날짜, 로트번호를 인용해 좁혀 묻는 방식으로 바꿨습니다. 문서 안에 언급된 다른 문서 이름을 따라가 원본 약 45종을 확보했고, 암호가 걸린 계약서는 코드 아트를 해독해 열었습니다. 관계자는 소개 경로를 따라 찾았고, 마지막 관계자인 인플루언서는 조직 관계도 문서와 계약서의 공식 창구 조항을 단서로 찾았습니다.

질문은 관계자별 발굴률 상승폭을 보며 배분했습니다. 상승이 멈춘 관계자는 줄이고, 질문 대비 효율이 높은 관계자에게 시간을 돌렸습니다. 말로만 나온 지식은 대화 내보내기에서 사실만 추려 지식 베이스에 넣었습니다.

## 3. 검증은 어떤 방식으로 하게 되었나요?

공개 TC 15개의 기대 대응을 항목으로 나누어 자동 시험했습니다. 가상 고객 LLM이 상황대로 대화하고, 채점 LLM이 답변과 실제 API 호출 기록을 항목별로 판정합니다. 틀린 대화만 고치지 않고 원인을 막는 일반 규칙으로 고쳤습니다. 시험은 액션 API 문서가 허용한 연습 호출 한도 안에서 진행했습니다.

최종 결과는 기대 대응 [ ]/[ ], 응답 속도 p95 [ ]초, 케이스당 말풍선 [ ]개, 말풍선당 평균 [ ]자입니다.

공개 TC만으로는 부족하다고 판단해 규정 문서에서 비공개 유형을 가정한 시나리오 42개를 만들어 같은 방식으로 시험했습니다. 프롬프트 인젝션 20종도 직접 시도해 지시문과 토큰이 유출되지 않는 것을 확인했습니다. 사진과 음성 첨부는 실제 카카오톡으로 확인했습니다.

## 4. 주요 설계와 구현 방법은 무엇인가요?

구조는 카카오톡 채널, FastAPI 웹훅, 에이전트, 액션 API, 카카오 콜백 순서입니다. 서버는 가비아 클라우드에 직접 배포했습니다. 모델은 두 후보를 같은 시험으로 비교해 Hive의 GLM 5.3 Flash를 선택했고, 오류가 나면 DeepSeek V4.1 Flash로 넘어갑니다.

첫 메시지의 case metadata에서 케이스 ID를 읽어 API 헤더에 넣고, 상담 인입 일시를 기준일로 판단합니다. 케이스가 바뀌면 대화 기억을 새로 시작합니다.

지식은 핵심 규정을 항상 넣고, 드물게 쓰는 문서와 인터뷰 기록은 대화와 관련된 것만 골라 넣습니다. 입력을 줄여 응답이 느려지는 것을 막기 위해서입니다. 고객의 말에 맞는 처리 절차는 답변 직전에 다시 제시해 자료가 길어도 절차를 건너뛰지 않게 했습니다.

속도는 생각 수준을 비교해 정확도를 유지하는 낮은 값을 선택했고, 조회는 병렬로 호출합니다. 호출이 늦어지면 같은 요청을 한 번 더 보내 먼저 도착한 답을 씁니다. 50초 안에 끝나지 않으면 안내 문구로 답해 60초 무응답을 막습니다. 긴 답변은 뜻을 유지한 채 자동으로 줄입니다.

보안은 지시문 유출 차단, 액션 서버 밖 호출 차단, 데이터 초기화 경로 차단을 코드로 넣었습니다. 개발에는 Claude Code를 활용했습니다.

## 5. 아쉬웠던 점과 한계점이 있다면 무엇이었나요?

낮은 생각 수준은 빠르지만 드물게 절차를 건너뜁니다. 상황별 절차로 줄였으나 키워드에 걸리지 않는 문의에서는 남을 수 있습니다.

모델 응답이 가끔 늦어져 p95가 시험마다 달랐습니다. 문서끼리 어긋나는 값은 정본 우선 규칙으로 처리했고, 끝까지 확보하지 못한 자료가 필요한 문의는 담당자 이관으로 넘깁니다.

자동 채점은 LLM의 판단이라 실제 심사와 다를 수 있습니다. 대화 중간에 고객이 시스템 형식의 문구를 직접 입력해 다른 계정을 사칭하는 경우는 정상 시나리오와 구분이 어려워 완전히 막지 못했습니다. 시간이 더 있었다면 이 부분과 비공개 유형 시험을 더 보강했을 것입니다.
